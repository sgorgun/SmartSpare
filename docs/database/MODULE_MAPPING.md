# SmartSpare — Database Ownership per Module (Stage 2 Plan)

Status: **analysis for stage 2 (data layer)**, decisions accepted in [ADR 0011](../adr/0011-database-ownership-per-module.md).
Inputs: [ARCHITECTURE_DECISIONS.md](../architecture/ARCHITECTURE_DECISIONS.md) sections 2, 4, 5; ADR [0002](../adr/0002-modular-monolith.md), [0003](../adr/0003-module-boundaries-and-integration-events.md), [0004](../adr/0004-hybrid-ef-core-code-first.md), [0009](../adr/0009-azure-hosting-and-delivery.md); [DATABASE_DESIGN.md](DATABASE_DESIGN.md); `db/bootstrap`, `db/migrations/V001–V016`, `db/seed/R001`, `db/testdata/T001`, `db/tests`.

This document maps every object of the current database (schema version 16) to the module that will own it, lists every dependency that crosses a module boundary and decides what replaces it, and splits the remaining stage 2 work into pull requests.

## 0. Summary of decisions

| # | Decision |
|---|---|
| D1 | Schema → module: `iam` → Identity; `catalog`, `inventory`, `raw`, `staging` → Inventory; `fleet` → Fleet; `procurement` → Procurement; `forecast` → Forecasting; `mart` → Reporting; `ref`, `util`, `audit` → Platform. `meta` is retired (replaced by EF migration history tables). |
| D2 | **Suppliers move to Procurement.** `catalog.supplier`, `catalog.supplier_part`, `catalog.supplier_price` become `procurement.supplier`, `procurement.supplier_part`, `procurement.supplier_price`. Section 2 of the architecture makes Procurement responsible for "suppliers and prices"; leaving them in `catalog` would make PO line validation (US12) and four-eyes approval (US14) read another module's schema. |
| D3 | **Platform is a shared kernel, not a module.** Foreign keys from module tables to `ref.*` stay (immutable, seeded reference data). Modules may call `util.*` and attach `audit.trg_row_audit`. The Platform never references a module (the FK `audit.audit_log.user_id → iam.app_user` is removed). On extraction, the Platform SQL is installed into each service database. |
| D4 | **All 33 cross-module foreign keys are removed** in stage 2 (section 2). The columns, their indexes and every intra-row CHECK stay; integrity moves to the owning module's handlers, read-only copies and events. |
| D5 | **Stage 2 is a structural port, not a behaviour change.** Cross-module *logic* (service-kit reservation, recommendation → transfer/PO, goods receipt, in-transit, stock position) is kept as clearly marked **transitional SQL** at the end of stage 2 so that the existing 97 assertions and the T001 demo data stay green. Each transitional object is replaced by an integration-event flow in the stage of its module (4–7) and removed there. |
| D6 | One DbContext per module plus a `PlatformDbContext`; each keeps its history in `<schema>.__ef_migrations_history`. Apply order: **Platform first, Reporting last**, the other five in between in a fixed order. Transitional cross-module views are created by the Reporting context, the only one allowed to read every schema. |
| D7 | SQL parts live in `db/sql/<context>/` and are embedded into the module assembly; migrations call them by resource name. Partitioned tables are created in SQL and mapped with `ExcludeFromMigrations()`. |
| D8 | Database roles: the current `app_*` capability roles are ported unchanged in stage 2. Per-module roles used with `SET ROLE` replace them in **stage 9** (together with Managed Identity), after the transitional cross-module functions are gone. |
| D9 | Database-side role and warehouse checks read transaction-local session GUCs set only by `SessionContextInterceptor`; the residual risk of self-set GUCs is closed by per-module roles in stage 9 (section 3.6). |
| D10 | Each module has a unit of work over its own DbContext; the transaction decorator resolves the module by the command's assembly, and integration events reach `outbox_message` in the same `SaveChanges` as the data (section 5.6, PR 2d). |

Every table also has an implicit identity sequence (`GENERATED BY DEFAULT AS IDENTITY`), created by EF with `UseIdentityByDefaultColumn()`; sequences are therefore not listed separately. There are no free-standing sequences: document numbers use the `util.document_counter` table.

## 2. Cross-module foreign keys

33 FK constraints cross a module boundary (counted as declared in the migrations; partitioned tables clone FKs per partition, so `pg_constraint` shows more). All are removed in stage 2 (D4). The column, its index and its CHECKs stay; the index keeps "history of one user / document" queries fast.

FKs **to the Platform** (`ref.*`) are kept by decision D3 and are not listed as cross-module: `catalog.part → ref.brand / ref.part_category / ref.unit_of_measure`, `inventory.stock_movement → ref.movement_type`, `iam.user_brand → ref.brand`, `fleet.machine_model → ref.brand / ref.machine_type`, `fleet.machine → ref.operating_condition`, `forecast.ml_model_version / benchmark_result → ref.demand_class`. In each module DbContext the `ref` entity is mapped read-only with `ExcludeFromMigrations()`.

## 3. Cross-module SQL logic

### 3.1 Every object that reads or writes another module's schema

Verdicts: **SQL-local** = stays in SQL inside one module after the stated change; **C#** = moves to a C# handler or query; **Events** = replaced by an integration-event flow (Outbox/Inbox). Stage = when the target design is implemented; until then the object is kept as transitional (section 3.2).

General pattern for SQL functions that must publish an event: the C# command handler calls the module-local SQL function inside its transaction and writes the outbox message through EF in **the same transaction** (the outbox table is in the module's own schema). SQL never writes JSON to the outbox directly.

### 3.4 UC01 as an event flow (replaces `forecast.decide_recommendation`)

1. The planner accepts or overrides a recommendation (`DecideRecommendation` in Forecasting). Forecasting records the decision in its own transaction (status `accepted` / `overridden`, `final_qty`, `decided_by`, reason) and writes **`TransferRequested`** (recommendationId, donor, recipient, part, quantity, proposed quantity, override reason, requestedBy) to its outbox. A reject stays module-local, as today.
2. Inventory's handler (Inbox for idempotency) creates the transfer order and approves it on behalf of `requestedBy` in one Inventory transaction — `inventory.approve_transfer` keeps the firm reservations, donor safety stock (US10, SS201) and lock ordering. The planner's accept *is* the approval (UC01 step 10–11), exactly as the current function does.
3. Success → **`TransferApproved`** (recommendationId, transferOrderId, number); Forecasting stores `transfer_order_id`. A recommendation that is accepted but has no document id yet is "awaiting fulfilment".
4. SS200/SS201 → **`TransferRejected`** (recommendationId, error code, message); Forecasting compensates: back to `open` with `decided_*` cleared (allowed by `ck_recommendation_decided`); the audit trail keeps the attempt.
5. Purchase recommendations follow the same shape: **`PurchaseRequested`** → Procurement consolidates into an open draft PO of the same supplier and hub (logic of today's `ELSE` branch, moved into Procurement) → **`PurchaseRequestAccepted`** (purchaseOrderId) or **`PurchaseRequestRejected`** (SS400/SS401/SS402).

### 3.6 Trust model of the session context (`app.user_id`, `app.user_roles`, `app.home_warehouse_id`)

After X1 and X2, the database-side role and warehouse checks (`util.require_role`, SS301; `dispatch/receive_transfer`, SS302) trust session GUCs instead of reading `iam`. This is the same trust model the audit trail already relies on for `app.user_id`:

- **Set only by the interceptor.** `SessionContextInterceptor` sets all three values at the start of every transaction from the authenticated principal (cookie claims issued by Identity). No code path builds them from request input, and no business function accepts a user, role or warehouse as a parameter.
- **Transaction-local.** The values are written with `set_config(name, value, true)`, so they disappear at commit or rollback and can never leak to the next user of a pooled connection. A transaction without them has no user: `util.require_app_user` raises SS301.
- **Only application logins can connect.** The bootstrap revokes `CONNECT` from `PUBLIC` and grants it only to `smartspare_api`, `smartspare_jobs`, `smartspare_reporting` and `smartspare_migrator`; none is superuser, and their credentials live in user-secrets / Key Vault. People and tools never connect with these logins.
- **The checks are defence in depth.** Authorisation is enforced first by the ASP.NET Core policies on every endpoint; the database checks catch bugs in the application, not a hostile client.

**Residual risk.** PostgreSQL lets any session set its own custom GUCs. Code that can run arbitrary SQL under an application login (for example after an SQL-injection bug or a stolen connection string) can claim any user or role and pass `util.require_role`. Until stage 9 the blast radius is the whole of `app_write`. **Stage 9 closes this with per-module roles (section 4.2):** a module role has no privilege outside its own schema whatever its GUCs say, the `SECURITY DEFINER` functions run under per-module owners, and the login is a Managed Identity without a password that could be stolen. The forged-GUC case is then limited to the operations one module's role may perform anyway, which is the boundary the API itself already has.

## 4. Database roles

### 4.1 Current roles (bootstrap + V015)

`app_read`, `app_write` (⊃ read), `app_ml` (⊃ read), `app_audit`, `app_admin` (⊃ write) are **capability** roles that span all schemas; logins `smartspare_api` (app_write), `smartspare_jobs` (app_write + app_ml), `smartspare_reporting` (app_read), `smartspare_migrator` (member of `smartspare_owner`). All objects are owned by `smartspare_owner`.

### 4.2 Target: one role per module, used with `SET ROLE` (ADR 0009)

| Target role (NOLOGIN) | Privileges | Replaces |
|---|---|---|
| `ss_identity` | `iam` read/write incl. personal-data columns; `iam.anonymise_user`; Platform helpers | `app_write` / `app_admin` on `iam` |
| `ss_inventory` | `catalog`, `inventory`, `raw`, `staging` exactly as `app_write` today (no direct writes to `stock_balance`, `stock_reservation`, ledger history); warehouses/routes as `app_admin` today; own outbox/inbox | `app_write`, `app_admin` (warehouses), `app_ml` (`expire_soft_reservations`) |
| `ss_fleet` | `fleet` as `app_write` today; own outbox/inbox | `app_write` on `fleet` |
| `ss_procurement` | `procurement` (incl. suppliers after D2) as `app_write` today; own outbox/inbox | `app_write` on `catalog.supplier*`, `procurement` |
| `ss_forecasting` | `forecast` as `app_ml` today (model activation only via `promote_model`), decisions as `app_write` today; own outbox/inbox | `app_ml`, `app_write` on `forecast` |
| `ss_reporting` | `SELECT` on all business schemas with personal data **only masked** (as `app_read` today), `mart.refresh_all`, masked audit view | `app_read`, `app_audit`, `app_ml` (mart refresh) |
| `ss_platform_admin` | `ref.*` writes, `audit.purge_expired` | `app_admin` on `ref`, `audit` |

Every module role gets `USAGE` on `util`/`ref`, `SELECT` on `ref.*` and `EXECUTE` on the Platform helpers. A module role has **no** privilege on another module's schema, so module boundaries are enforced by PostgreSQL itself (architecture section 7). Application roles of users (BRAND_MANAGER, …) stay application roles checked by ASP.NET policies and `util.require_role`; they are not database roles.

Schema ownership: per-module owner roles (`ss_inventory_owner`, …) would make `SECURITY DEFINER` functions run with module-only rights. They are introduced together with the module roles; until then `smartspare_owner` owns everything.

How `SET ROLE` is applied: each module's DbContext registers a `DbConnectionInterceptor` that runs `SET ROLE ss_<module>` when a connection is opened. Npgsql resets the session (`DISCARD ALL`) when a connection returns to the pool, so a pooled connection never leaks a module role. One Managed Identity login (`smartspare_app`) is a member of all module roles; after a split each service gets its own identity with one role.

### 4.3 Stage 2 or stage 9?

**Stage 9.** Reasons:

1. The transitional functions of section 3.2 deliberately write across schemas; per-module roles (and per-module owners) would break them. Roles can only be enforced once stages 5–7 have replaced them.
2. The login side (Managed Identity, Microsoft Entra authentication to PostgreSQL, `SET ROLE` membership) is Azure work that belongs with Bicep and the first deployment.
3. Tests T03 assert the current role model (22 assertions); changing it together with the structural port would mix two verifications.

Stage 2 therefore ports the current roles and grants 1:1 (split by object owner) and grants the new outbox/inbox tables to `app_write`/`app_ml`. Stages 4–8 keep a per-module grants file current, so stage 9 only has to create the module roles, move the grants and update `util.v_privilege_findings` and T03.

### 5.2 Order

`Platform → Identity → Inventory → Fleet → Procurement → Forecasting → Reporting`.

Required: **Platform first** (extensions, `util` helpers, `ref` tables, `audit.trg_row_audit` used by all module triggers) and **Reporting last** (marts and transitional views read every schema). Without cross-module FKs, the five business modules have no creation-time dependency on each other; their order is fixed only for determinism. A single list in the host (`ModuleCatalog`) defines the order for local runs, CI and the pipeline.

### 5.4 Partitioned tables

`inventory.stock_movement` (60 months from 2024-01 + default) and `audit.audit_log` (48 months from 2025-01 + default):

- The parent table, its partitions, indexes, FKs (intra-module and to `ref`) and triggers are created in SQL at the **top** of the owning initial migration, by the same statements as today (`util.ensure_monthly_partitions`). Index names created on partitions are kept identical, because T04 asserts them (`part_id_warehouse_id_occurred_at_idx`, `table_name_record_id_occurred_at_idx`).
- EF maps the entity to the parent with `ToTable(..., t => t.ExcludeFromMigrations())`, composite key `(id, occurred_at)`; inserts and reads go through the parent.
- `inventory.demand_exception` is created by EF after that SQL; its composite FK to the ledger is created by EF (the referenced table exists by then).
- Future partitions: a Quartz job calls `util.ensure_monthly_partitions` monthly (12 months ahead); `audit.purge_expired` drops expired audit partitions. Partitions are never part of the EF model.

### 5.5 Who runs the migrations, and as whom

- **Owner.** Migrations must create objects owned by `smartspare_owner`, as today. The migration connection string sets the session role at start-up (`Options=-c role=smartspare_owner`); the login `smartspare_migrator` is a member of the owner role and is not a superuser. **Verified in PR 2b** on PostgreSQL 17: with this option `current_user` is `smartspare_owner` and every Platform object and the history table are owned by it (integration test `PlatformObjects_AreOwnedByTheOwnerRole_NotByTheMigratorLogin`). Fallback if a platform rejects the start-up option: set `Migrations:OwnerRole` to empty and add a `DbConnectionInterceptor` to the runner's contexts that runs `SET ROLE smartspare_owner` in `ConnectionOpened`; Npgsql resets the session (`DISCARD ALL`) when the connection returns to the pool, so the role never leaks.
- **Concurrency.** EF Core takes a migration lock per context; the order list (5.2) runs contexts sequentially. The provider's lock leaves no table behind (the schema diff of PR 2b shows only the history table); parallel runners are not exercised, because the runner is single-instance by design (one CI job, one AppHost resource, one pipeline step).
- **Local (Aspire AppHost).** The `SmartSpare.MigrationRunner` console project (`src/Bootstrapper/`, development and CI only) runs the cluster bootstrap when the migrator login or the database is missing, then applies all contexts in the order of `SmartSpare.ModuleCatalog` (shared with the host). The AppHost starts it after PostgreSQL is up and starts the host only after it has finished (`WaitForCompletion`). Aspire does not create the database: the bootstrap does, owned by `smartspare_owner`. The runner interprets the psql bootstrap script itself (`\set`, `:'var'`, `\gexec`), so the same file is still run by hand with psql on Azure; the login passwords are Aspire parameters generated once and persisted in the AppHost user secrets, and the host connects as `smartspare_api`. The host itself never migrates (ADR 0004). Demo data (T001) is loaded on demand by a separate AppHost command / script, not on every start.
- **CI.** The integration-test job starts PostgreSQL 17 (Testcontainers), runs bootstrap, applies all contexts in order through the same runner, loads T001 and runs the SQL suite and the .NET integration tests. The build job runs `SmartSpare.MigrationRunner check-model`, which calls `Database.HasPendingModelChanges()` (the API behind `dotnet ef migrations has-pending-model-changes`) for every context of the catalogue, so a model change without a migration fails the build and new contexts are covered without editing the workflow.
- **Azure (stage 9).** CI builds one EF migration bundle per context (`dotnet ef migrations bundle --context … --self-contained -r linux-x64`) as pipeline artefacts. The deployment job runs them in the order of 5.2 as `smartspare_migrator` (connection string from Key Vault, later Entra token), **before** the new image is deployed. Bootstrap runs once per server by the server admin. A failing bundle stops the deployment; each migration is transactional, so the database stays at the previous version.

### 5.6 Unit of work and the transaction decorator

Today `TransactionCommandDecorator` only passes the call through, because no DbContext exists yet. PR 2d makes it real:

- **Per-module unit of work.** Each module registers an `IUnitOfWork` over its own DbContext (scoped). It is `internal` to the module; the Infrastructure building block only defines the abstraction and a generic `EfUnitOfWork<TContext>`.
- **Module resolved by assembly.** At start-up every `ModuleInstaller` registers its assembly together with its unit of work. The transaction decorator looks up the module of the command by `typeof(TCommand).Assembly`, opens that context's transaction (inside the execution strategy, because `EnableRetryOnFailure` forbids user-initiated transactions outside it), runs the handler, commits on success and rolls back on a failed `Result` or an exception. A command whose assembly has no registered module fails at start-up, not at run time.
- **Outbox in the same `SaveChanges`.** Handlers do not publish directly; they add integration events to the unit of work. A `SaveChanges` interceptor in the module context turns them into `outbox_message` rows of the module's schema, so the data change and its outbox rows are written by the same `SaveChanges` and committed by the same transaction. SQL functions called by the handler (section 3.1) run on the same connection and transaction, so they are covered too.
- **Session context.** The decorator's transaction is the one `SessionContextInterceptor` hooks into, so `app.user_id`, `app.user_roles` and `app.home_warehouse_id` are set for every command (section 3.6).
- **Proof.** An integration test (Testcontainers) runs a test command that changes data and raises an integration event, then fails: afterwards neither the data row nor an `outbox_message` row exists. A second test runs the successful variant and finds both, committed together.

### 7.1 Changes made while implementing 2b and 2c

The scope of 2b and 2c is as planned. Implementation details that differ from sections 1–5, and why:

- **No FK indexes by convention (2c).** Module contexts remove EF's `ForeignKeyIndexConvention` and declare every index with its V016 name. Otherwise EF would add indexes that V016 does not have.
- **`uq_customer_erp_ref_hash` in SQL (2c).** It is a UNIQUE constraint on a nullable column. EF can model it only as a unique *index* (a different object) or as an alternate key (which makes the column required), so `db/sql/fleet/0001_fleet_logic.sql` adds the constraint.
- **Two CHECKs use their V005/V010 source text (2c).** PostgreSQL's catalogue form of `col IN (...)` on a varchar column does not normalise to itself, so `ck_demand_exception_method` and `ck_import_error_code` keep the original expression.
- **The ledger's intra-module FKs are added after the EF tables (2c).** `inventory.stock_movement` is created before the EF tables (`demand_exception` references it); its FKs to `warehouse`, `part`, `transfer_order_line` and `import_batch` follow in `0003_stock_movement_fks.sql`. The dump is identical.
- **History tables are readable by `app_read` in catalog/inventory/fleet (2c).** V015's `GRANT SELECT ON ALL TABLES IN SCHEMA …` also covers them. This keeps `util.v_privilege_findings` empty; documented in `tools/schema_diff.allow`.
- **Migrations are `internal` and treated as generated code (2c).** A module may expose only its installer (architecture test), and analyzers skip the scaffolded `Migrations/` folders (`.editorconfig`).
- **Model check in CI (2b)** uses `MigrationRunner check-model` (`HasPendingModelChanges()` for every catalogue context) instead of calling `dotnet ef` per context.
- **Schema diff result after 2c:** 2,724 statements identical across `ref`, `util`, `audit`, `iam`, `catalog`, `inventory`, `raw`, `staging`, `fleet`. The differences, all documented:
  - 20 removed cross-module FKs;
  - 53 statements of the supplier tables (2d);
  - 25 statements of the transitional views and functions (2d);
  - 5 statements of `audit.v_audit_log_masked` (2d);
  - 14 statements of the EF history tables.
